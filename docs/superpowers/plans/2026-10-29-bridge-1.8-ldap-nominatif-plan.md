## Approach

Volet serveur Farois (migration N+1) + volets plugin, même chantier. `bureau_etudes` devient un **rôle groupe NOLOGIN** (grants mig 335 inchangés, pattern `ftth_editor`, jamais de `PASSWORD`) ; rôles LOGIN nominatifs `IN ROLE` créés par admin ; authentification par les lignes `ldap` (même serveur/suffixe que wyre), restreintes à `+bureau_etudes`. L'exclusion GIS de 083 (nom exact `bureau_etudes`, l.86/134) est étendue au **groupe** par un test sûr (faux pour `postgres`/`ftth_admin` en premier). Pas de `ref.users` pour les externes, donc pas d'activation via l'UI : création manuelle par admin (faible volume) + réconciliation automatique qui passe `NOLOGIN` les rôles sortis du groupe AD BE (jamais de création auto en `LOGIN`). La migration ne coupe jamais : `NOLOGIN` = geste ops séparé à la publication.

Côté plugin, logique pure testable sans QGIS (`bridge_nominatif.py`, pattern Bridge 0), partagée par les deux connexions. wyre : Auth Manager Basic `9i19s56` avec `username=<login>`, sonde psycopg2 + lecture SQLSTATE classe `28`, 1 ressaisie, repli D7 mémorisé en settings. be : Auth Manager `07254s7` nominative, même sonde (1 ressaisie, anti-verrouillage AD identique), pas de repli (coupure nette). `root.crt` commun par upsert de blocs PEM (CA Farois + racine AD, calqué sur `upsert_pgpass_entry`), `verify-full` (`"5"`) sur les deux connexions, échec bloquant si `root.crt` non écrit.

Scopes : le serveur filtre déjà (RLS 502 dès J1, `v_duct_progress` et `v_element_documents_list` en `security_invoker` — vérifié) ; le plugin **lit** les capacités/périmètres de session (`ref.role_capabilities`, `ref.user_data_scopes`, SELECT conservé aux nominatifs par F19 — vérifié) et les **rend visibles** : couches en lecture seule sans `network.write`, périmètre affiché, couches système vérifiées (`v_form_lists` sans invoker mais sans portée MRO/POP — vérifié sans impact).

## Révision 29/10 après revue

Revue adversariale de la branche (`bf5b45f`) puis décisions de Simon du 29/10. Ce qui suit **remplace** les points du plan et du spec cités ; le reste est inchangé.

### D-TLS-1 — CA dans la base d'authentification QGIS, plus de `root.crt` (écart au plan B6 et au spec §5.5 / §5.7.3)

- **Raison** : pour une couche `authcfg` (méthode Basic) en `sslmode=verify-*`, QGIS **remplace** tout `sslrootcert=` de la datasource par un fichier temporaire `tmp_basic_<uuid>.pem` qui contient `QgsAuthManager.trustedCaCerts()` — magasin système + CA de la base d'authentification QGIS ayant une politique de confiance (`QgsAuthBasicMethod::updateDataSourceUriItems`, identique en 3.28 et sur master). Le `root.crt` de libpq n'est donc jamais lu par les couches, l'entrée navigateur ni les projets : toutes les connexions nominatives `9i19s56`/`07254s7` auraient échoué (« certificate verify failed ») alors que la sonde psycopg2 réussissait.
- **Fait** : `_ensure_qgis_trusted_cas()` importe `certs/farois-db-ca.crt` et `certs/constructelbe-ca.pem` (`storeCertAuthority` + `storeCertTrustPolicy(…, Trusted)` + reconstruction des caches CA, politiques et confiance), idempotent (`certAuthority(shaHexForCert)` ; `existsCertAuthority` interroge une colonne inexistante en 3.28). Ni l'un ni l'autre n'exige le mot de passe maître (vérifié dans le source 3.28 et master). La sonde psycopg2 lit `certs/root-ca-bundle.pem` **en place dans le paquet** ; plus aucune écriture sur le poste (`upsert_root_crt_pem`, `_ensure_root_crt` retirés). Échec de l'import = nominatif impossible → repli partagé + bandeau + journal (au lieu du « message bloquant » du spec §5.7.3 : AC produit « jamais de poste bloqué »).
- **À noter** : la CA Farois devient une CA de confiance de **tout** QGIS (HTTPS compris), pas seulement de PostgreSQL. Sa clé privée reste sur le serveur (§5.5) ; une compromission de cette clé permettrait aussi d'intercepter le HTTPS de QGIS sur les postes.
- **Recette** : `scripts/qgis_smoke.py` vérifie en vrai QGIS (3.28 / 3.44 / 4.x) que la CA Farois est dans le `sslrootcert` produit par `updateDataSourceUriItems` pour une config Basic en `verify-full`, et qu'un second import ne duplique rien.

### D-TLS-2 — `verify-full` pour le nominatif seulement ; identifiant partagé en `require` comme 1.7.x (écart au spec §5.5 « verify-full partout »)

- **Raison** : le risque protégé par `verify-full` est la capture du **mot de passe AD** (§5.1). L'identifiant partagé `ftth_editor` (repli D7, secours admin D5) se comporte exactement comme en 1.7.x : `sslmode` de `credentials.json` (`require` par défaut) pour psycopg2, entrées navigateur `wyre`/`be` en `"3"`, init de projet, styles, couche `v_form_lists`, pré-cache. Le ruling « verify-full appliqué aussi à la connexion partagée » est annulé ; les 4 tests `test_bridge1b_wiring` reviennent à leur contenu 1.7.7.
- **Conséquence prise en charge** : les projets 1.7.x et ceux enregistrés en mode partagé portent `sslmode=require authcfg=9i19s56`. Sur un poste dont `9i19s56` porte le mot de passe AD, QGIS ouvrirait leurs couches en `require` (serveur non vérifié) **avant** `_fix_layer_credentials`. Un préprocesseur `QgsPathResolver` (appliqué par QGIS à chaque datasource lue dans un projet, avant la création de la couche ; disponible 3.10+, retrait 3.22+) force `verify-full` sur les datasources de nos serveurs rattachées à `9i19s56`/`07254s7` tant que ces configs portent le mot de passe AD. Il ne touche à rien d'autre et ne lève jamais.

### Transition et rollback (I11)

- **Projet enregistré en nominatif ouvert sur un poste 1.7.x** (ou après rollback) : datasource `user='<login>' sslmode=verify-full authcfg=9i19s56`. QGIS charge d'abord la couche avec `9i19s56` du poste (identifiant partagé) en `verify-full` : échec si la CA Farois n'est pas dans la base d'authentification de ce QGIS (poste jamais passé en 1.8). 1.7.x réécrit ensuite la couche en identifiant partagé **en clair** (`password=`) en gardant `verify-full`, sans `root.crt` : échec. Les couches de ces projets sont donc invalides sur un poste 1.7.x. Contournement : ouvrir le projet depuis un poste 1.8, ou modifier `sslmode` à la main. À annoncer avant la publication (projets partagés inter-postes pendant la transition).
- **Rollback 1.8 → 1.7.7** : `9i19s56` (et `07254s7`) peuvent porter **login nominatif + mot de passe AD**. 1.7.7 relit ce mot de passe au démarrage et tente `ftth_editor` avec : refus (ligne `scram`, aucun bind AD), plugin non connecté jusqu'à « Connecter » (qui réécrit `9i19s56` en `ftth_editor` + mot de passe partagé). Entre-temps, les couches `authcfg=9i19s56` d'un projet ouvert se connectent **en `<login>` avec le mot de passe AD en `require`** (1.7.7 n'a pas le préprocesseur). Procédure de rollback : faire « Connecter » une fois sur chaque poste, ou supprimer les configs `9i19s56`, `07254s7` et `nomin18` du gestionnaire d'authentification QGIS (ou publier une 1.7.8 qui le fait au démarrage). La CA Farois importée reste dans la base d'authentification QGIS (inoffensive).
- **Mode mémorisé** : `constructel_bridge/auth_mode` et `constructel_bridge/pg_login` ne sont lus que par 1.8 ; 1.7.x les ignore.

### Machine d'état révisée (rappel des comportements)

- Seul le **refus du mot de passe** (`password`/`LDAP authentication failed`, anglais ou français) déclenche la ressaisie (une seule, ≤ 2 binds refusés par démarrage) ; tout autre échec (NOLOGIN, rôle inconnu, `pg_hba`, délai — `connect_timeout` 10 s —, TLS, trop de connexions, motif inconnu) mène au repli partagé quand il existe.
- Mot de passe AD mémorisé (`nomin18`) seulement après succès ou login non actif ; un mot de passe refusé est retiré de `nomin18`/`9i19s56`/`07254s7` et n'est jamais rejoué. En repli sans identifiant `be` partagé, `07254s7` nominative est retirée.
- Plus rien de modal ni de réseau dans `initGui` : phase silencieuse à `layerLoaded(0, n)` pour un projet passé en ligne de commande (ouvert par `main.cpp` avant `completeInitialization()`), sinon à `initializationCompleted` — qui passe aussi AVANT l'ouverture du « dernier projet » (`QgisAppInterface` relaie le signal avant que `setupConnections()` ne branche `fileOpenAfterLaunch` ; corrigé en revue 2, M6) ; dialogue, assistant d'accueil et bandeau (sans expiration) ensuite.
- Annuler le dialogue ne mémorise rien : nouvelle demande au démarrage suivant. Un poste en repli dont le mot de passe a été refusé n'a plus de dialogue d'office : « Réessayer mon accès nominatif » (libellé du menu = indication permanente du mode partagé).
- Verrou lecture seule (D2) limité au schéma `wyre`, levé quand la session ne l'exige plus, jamais écrit dans le projet.

### Limites restantes

- **Utilisateur sans rôle PostgreSQL** (pas encore synchronisé par `ldap_sync`) : le serveur répond « password authentication failed » (ligne `scram`, aucun bind AD) — indiscernable d'un mauvais mot de passe. Après deux refus, le poste reste en repli sans mot de passe mémorisé : une fois le rôle créé et activé, il faut « Réessayer mon accès nominatif » (pas de bascule automatique au redémarrage pour ce cas ; elle existe pour un rôle `NOLOGIN` activé ensuite, AC8).
- **Panne réseau totale** : la sonde (≤ 10 s) puis la connexion partagée (sans délai, comme 1.7.x) échouent toutes deux ; un projet ouvert au lancement attend la sonde.
- **Pré-cache `QgsCredentials`** : posé en session partagée seulement ; il ne peut pas être retiré si la session redevient nominative dans la même session QGIS (pas d'API).
- **Validation en vrai QGIS / vraie base** à faire en recette : bandeau persistant et libellé du menu, `layerLoaded(0, n)` avant la première couche d'un projet ouvert au lancement, préprocesseur sur un `.qgz` 1.7.x, messages serveur en français, verrou `wyre` et `readOnly` absent du projet enregistré.

### Revue 2 (29/10, sur `ec97944`) — compléments

Corrigé dans le code (détail dans les messages de commit) :

Contrôle de recette : `SELECT f_table_schema, f_table_name, stylename FROM public.layer_styles WHERE styleqml::text LIKE '%readOnly="1"%';` doit être vide ; piste Farois (backlog) : refuser ou nettoyer `readOnly="1"` dans `layer_styles`.

Non corrigé, justifié :

- **M5 (panne réseau = sonde 10 s puis tentative partagée)** : le cas coûteux (~21 s sous Windows) est le SYN sans réponse, que libpq signale par « timeout expired » — le même message qu'un annuaire AD en panne, `connect_timeout` couvrant aussi l'authentification. Sauter la tentative partagée sur ce message laisserait le poste déconnecté pendant une panne AD, le cas que le repli doit couvrir. Les cas distinguables (connexion refusée, DNS, hôte injoignable) échouent déjà vite, et leurs messages sont localisés par Windows. Statu quo.
